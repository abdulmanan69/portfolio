Why AbuseBox?

Most blacklist tools check one thing at a time. AbuseBox gives you a single pane of glass to:

  • See what needs attention in one list: blacklist listings, expiring certificates and domains, servers down, weak email security
  • Scan 60 DNSBL providers in seconds
  • Get AbuseIPDB reputation scores alongside blacklist results
  • Run bulk checks on up to 300 IPs/domains at once (paste or upload TXT/CSV/XLSX)
  • Scan entire subnets (CIDR /24) for blacklisted IPs
  • Pull WHOIS, DNS records, and SSL certificate details with one click
  • Validate SPF / DKIM / DMARC email authentication
  • Check if a server is up or down with DNS, port, and HTTP checks
  • Register assets and run all checks with configurable toggles
  • Schedule periodic checks with email, Slack, Discord or webhook alerts for listings, recoveries, outages and expiry
  • Keep an activity log of every change and compare any two checks
  • Export results to CSV and track history with charts
  • Switch between light and dark mode

No vendor lock-in. No paid tiers. Self-host it and own your data.

Quick Start

Docker (recommended)

git clone https://github.com/bekkaze/abusebox
cd abusebox
cp backend/.env.example .env    # configure your settings
docker compose up --build

Open http://localhost:3000 and you're ready to go.

Default login: admin / password123. Change it in Settings right after the first sign-in.

To open AbuseBox from another machine, add that hostname or IP to VITE_ALLOWED_HOSTS and APP_CORS_ALLOWED_ORIGINS in .env.

Upgrading from v1.1.x

Back up your data first, then pull the new version. The database is migrated automatically on start.

# The volume is named <folder>_abusebox-data; `docker volume ls` shows it.
docker run --rm -v abusebox_abusebox-data:/data -v "$PWD":/backup alpine tar czf /backup/abusebox-data.tgz -C /data .
git pull
docker compose up -d --build

Things that changed:

  • Everyone is signed out once. Older Docker setups used a published JWT secret; v1.2.0 generates a private one (or uses your APP_SECRET_KEY).
  • Change the admin password. Older Docker setups ignored DEFAULT_ADMIN_PASSWORD from .env, so the admin account probably still uses password123. A banner reminds you until you change it in Settings → Security.
  • The /tools/* API needs a token. Only /blacklist/quick-check/ stays public. See API Endpoints.
  • No public sign-up. Admins add users in Settings → Users.
  • The scheduler is on by default unless you turned it off in Settings before.

Snort3 integration

AbuseBox works in both directions with Snort3: alerts flow in for correlation, and detection rules flow back out.

   Snort3 sensor                 AbuseBox                    Snort3 sensor
        |                            |                            |
        |  alert_json --> agent -->  |  correlate to assets       |
        |                            |  deduplicate floods        |
        |                            |  triage queue              |
        |                            |                            |
        |                            |  generate rules ---------> |
        |                            |  from blacklists,          |
        |                            |  repeat attackers,         |
        |                            |  lookalike domains         |

Sending alerts from a sensor

  1. Configure Snort3 to write JSON alerts. A working snort.lua and a starter local.rules are in deploy/snort/:

    alert_json = {
  file = true,
  limit = 100,
  fields = 'timestamp pkt_num proto pkt_gen pkt_len dir src_addr src_port dst_addr dst_port service rule action msg priority class'
}

  2. Create an API key in Administration → API keys with the snort:ingest scope. The plaintext is shown once; only a SHA-256 digest is stored.

  3. Run the agent on the sensor host. It needs nothing beyond Python 3:

    export ABUSEBOX_URL=https://abusebox.example.com
export ABUSEBOX_API_KEY=abx_...
./deploy/snort3-agent.py --log /var/log/snort/alert_json.txt --sensor dmz-01

    The agent checkpoints its byte offset and the log's inode, so it resumes after a restart, follows log rotation, and retries with backoff when the server is unreachable rather than dropping alerts.

No sensor to hand? Use Import log on the Intrusion Alerts page to replay an existing alert file, or POST raw text to /snort/ingest/raw/.

What happens to an alert

  • Deduplicated on sensor|gid:sid|src|dst inside a time window. A port scan produces thousands of identical alerts; the first is stored and the rest increment hit_count. Ports are excluded from the key on purpose, since a scan varies the port on every packet.
  • Correlated to a monitored asset when either endpoint matches. Domain assets are resolved, and that IP-to-asset index is cached for five minutes so ingest stays fast.
  • Graded from Snort's priority: 1 to critical, 2 to high, 3 to medium, 4 and above to low.

Generating rules

The Rule Generator builds a deployable ruleset from what AbuseBox has already found:

Source Rule produced
Blacklisted assets Alert on traffic involving the asset
Repeat attackers Alert on source IPs that keep triggering critical/high alerts
Lookalike domains Alert on DNS queries and HTTP Host headers for the lookalike

Generated SIDs start at 9000000 - clear of the vendor range (up to 1000000) and the conventional local range (1000000-1999999) - so a rule update never collides. Private and reserved addresses are never turned into rules, because such a rule would alert on ordinary internal traffic.

Domain rules match the longest label rather than the dotted name: DNS puts length-prefixed labels on the wire, so the bytes for paypa1.com are \x06paypa1\x03com\x00 and the dotted string never appears in the packet.

# Deploy an exported ruleset
cp abusebox.rules /etc/snort/rules/
# add to snort.lua:  include $RULE_PATH/abusebox.rules
snort -c /etc/snort/snort.lua -R abusebox.rules -T   # validate before reload

The built-in validator catches the structural mistakes Snort rejects, but it is not a substitute for snort -T: only Snort can confirm a rule loads against your configuration.

Running Snort3 with Docker Compose

docker compose --profile snort up -d

Snort has to see the traffic it inspects, which a bridge network hides, so that profile uses the host network namespace with NET_ADMIN/NET_RAW and reads SNORT_IFACE. On Docker Desktop (macOS/Windows) there is no host interface to tap: run Snort3 on the monitored host itself and point only the agent at AbuseBox.

Enterprise deployment

Roles

Authorisation is enforced on the server. The interface also hides what a role cannot do, but that is a convenience, not the control: a viewer who crafts the request by hand still gets a 403.

Role Can
viewer Read dashboards, scan results and alerts. Change nothing.
analyst Run scans, manage assets, acknowledge alerts, generate rules.
admin Everything, plus users, API keys, settings and retention.

New accounts default to viewer. Accounts created before roles existed are assigned one at startup from their previous admin flags, so an upgrade never locks out an administrator. An admin cannot demote or deactivate their own account, and the last active admin cannot be removed.

API keys

Sensors and CI jobs cannot complete an interactive login, so they authenticate with a scoped key in the X-API-Key header. Keys carry snort:ingest, scan:read or scan:run; usage (count, last IP, last time) is tracked so an unused or compromised key is visible. Revoked keys are kept rather than deleted, so the audit trail still resolves which credential performed a past action.

Audit trail

Append-only, admin-only, and separate from the asset activity log. It records logins and failed logins (by attempted username, so credential stuffing is visible), user and role changes, key issuance and revocation, alert triage and rule exports - each with actor, source IP, user agent and outcome.

Retention is deliberately manual (Administration → Data retention) rather than automatic, so deleting audit history is an attributable act. That operation is itself audited.

Self-hardening

AbuseBox ships a scanner that grades other people's security headers, so it sets the same ones on its own responses: a strict Content-Security-Policy, X-Frame-Options, nosniff, Referrer-Policy, Permissions-Policy and the cross-origin isolation headers. The Server banner is suppressed.

HSTS is sent only when the request arrived over TLS. Sending it over plain HTTP would tell a browser to refuse http://localhost for a year, which breaks local access in a way that persists long after the header is removed.

PostgreSQL

SQLite is fine for a single operator but serialises writers, and the background scheduler writes alongside the API. For anything multi-user:

docker compose --profile postgres up -d
# then in .env:
DATABASE_URL=postgresql+psycopg2://abusebox:<password>@postgres:5432/abusebox

Metrics

GET /metrics exposes Prometheus counters and latency histograms. It is unauthenticated on purpose: a scraper is usually a sidecar that cannot hold a credential, and the output is counters only, with no scan results, hostnames or alert contents. Restrict it at the network layer if your deployment needs that.

Series are labelled by matched route template, not raw path, so /snort/alerts/{alert_id} is one series rather than one per alert id.

Not included

Stated plainly, because a half-built version of any of these would be worse than none: SSO/SAML/OIDC, multi-tenancy (one organisation per deployment) and HA/clustering (a single API container; Postgres can be made highly available independently). Rate limiting currently covers login and the public blacklist check, not every endpoint.

External scanners

Eight industry tools feed one normalised finding model. How each is driven depends on what the tool actually permits - stated plainly, because the difference matters when planning a deployment.

Tool How it runs What you need
Nmap In this container Nothing. Installed in the image.
Ncat In this container Nothing. Installed in the image.
OpenVAS / Greenbone Live over GMP Your own Greenbone server, or the bundled compose profile
Rapid7 Nexpose / InsightVM Live over REST API v3 Your licensed console
Microsoft MBSA Live via the Windows connector A Windows host with MBSA installed
GFI LanGuard Live via the Windows connector A Windows host with LanGuard installed
Titania Nipper Live via the Windows connector A licensed host with Nipper installed
Core Impact Live via the Windows connector A licensed host with Core Impact installed

Every one of them is driven by the platform. Nothing is import-only, though a manual XML upload still works for all eight and goes through the same parser, so both routes produce identical findings.

Nmap and Ncat

Both run inside the backend container and need no configuration.

Nmap offers five profiles - Quick, Standard, Service detail, Vulnerability scripts and Host discovery - each with its own timeout. Callers pick a profile; they never supply nmap arguments. That removes a whole class of attacks based on nmap's own options, and keeps scans predictable.

Ncat grabs service banners, including over TLS with SNI, and can send a protocol probe to services that stay silent until spoken to.

Safety, since this is where user input reaches a subprocess:

  • An argument list, never a shell string, so there is nothing to inject into
  • Named profiles only; no raw flags are ever accepted
  • Targets pass the same public-address guard as the rest of the platform, so loopback, link-local and cloud-metadata addresses are refused
  • Output goes to stdout (-oX -), so no user-controlled path is written
  • Every profile is bounded by a timeout

OpenVAS / Greenbone (live over GMP)

Speaks the Greenbone Management Protocol directly: XML over a TLS socket on port 9390, the same protocol gvm-tools uses. Implemented against the standard library rather than python-gvm, because the surface used here is six commands and a security tool benefits from one less dependency.

# Stand up Greenbone Community Edition
docker compose --profile openvas up -d
# The first start downloads a multi-GB feed. Allow 30-60 minutes.

Then in .env:

OPENVAS_HOST=greenbone
OPENVAS_USERNAME=admin
OPENVAS_PASSWORD=your-password

From Network Scanning -> OpenVAS you can start a scan, poll its progress and pull the report. A scan runs for minutes to hours, so the API starts the work and returns a task id rather than holding an HTTP request open.

The live pull and a manual XML upload go through the same parser, so both produce identical findings.

Rapid7 Nexpose / InsightVM (live over REST)

Drives the console you already licence, via API v3.

NEXPOSE_URL=https://console.example.com:3780
NEXPOSE_USERNAME=admin
NEXPOSE_PASSWORD=your-password

Scans run against a site, not a free-form address: the console owns what is in scope, which is the right place for that decision. It also means this integration cannot point a licensed scanner at something the console was never configured to assess.

MBSA, LanGuard, Nipper and Core Impact (live via the connector)

These four are licensed desktop products and cannot run in a Linux container. What they do have is a scriptable interface, so deploy/windows-connector.py runs on the Windows host where they are installed, invokes them, and posts the results back. Standard library only, so there is nothing to install on the scanning host.

setx ABUSEBOX_URL      https://abusebox.example.com
setx ABUSEBOX_API_KEY  abx_...

python windows-connector.py --tool all --target localhost
python windows-connector.py --tool nipper --config-file C:\configs\router.conf

Create the key in Administration -> API keys with the snort:ingest scope. Run it from Task Scheduler and the findings stay current without anyone exporting a report by hand.

Core Impact is the awkward one, because its automation surface varies by version and licence, so the connector offers two modes:

rem Drive the console's Python automation to run an RPT
python windows-connector.py --tool core-impact --target 192.0.2.10

rem Or watch the console's report folder and ship anything new
python windows-connector.py --tool core-impact --report-dir "C:\Core Impact\reports"
eports"

Harvest mode is checkpointed by modification time, so a scheduled run does not re-upload the same assessment every time it fires. Use it if you are unsure: it works on every licence, including ones with scripting disabled, and still means nobody exports a report by hand.

Importing a report

Any supported tool's XML export can be dropped into Network Scanning -> Import. The format is auto-detected from the document, so you do not have to say which tool produced it.

Two detection notes worth knowing: Nipper and OpenVAS both use <report> as their root element, so Nipper is identified by its <part><section> structure and OpenVAS is required to show an actual <result>. Nexpose must be exported with the XML Export 2.0 template, which is the one that includes the <VulnerabilityDefinitions> block the parser joins against.

HTML and PDF reports cannot be parsed. Maximum 8 MB.

One severity scale

Eight tools means eight severity vocabularies: Nexpose grades 0-10, OpenVAS says "High" and also gives CVSS, MBSA says "Check failed", Nipper says "Critical", and nmap has no severity concept at all.

Two rules keep the mapping honest:

  • CVSS wins when present. A numeric score is objective; a vendor's word for it is partly a marketing decision. The original label is still stored on the finding, so nothing is lost.
  • Unknown maps to info, never to critical. A parser meeting a severity string it does not recognise must not manufacture an emergency.

Cross-tool correlation

This is what the normalisation is for. Findings are grouped on a fingerprint keyed on the CVE where there is one - the only identifier different vendors reliably agree on - and on a normalised title where there is not.

Findings -> Confirmed by more than one tool then answers the question that actually matters: where do independent scanners agree? Two tools reporting the same CVE on the same host and port is a far stronger signal than either alone, and a finding only one tool saw is the first thing to verify by hand.

Where tools disagree about how bad something is, that disagreement is shown rather than silently resolved in favour of one of them.

Contextual risk prioritisation

Eight scanners produce findings that repeat and contradict each other, and the usual answer - sort by CVSS - cannot express the three things that decide what actually gets fixed first: whether the finding is real, whether anyone is attacking it, and whether your own analysts would dismiss it.

Dashboard -> Risk Prioritisation answers those separately and shows its working:

  • Is it real? Dempster-Shafer evidence fusion across every scanner that looked, each discounted by a reliability figure learned from your triage. The output is a belief interval, not a point score, so "one tool said so and nothing corroborated it" is visibly different from "four tools agree".
  • Is anyone exploiting it? Snort3 alerts are joined to findings on host and port. A host appearing as the source of attack traffic is treated as a suspected compromise and listed above everything else.
  • Would an analyst dismiss it? A logistic-regression model trained on your own confirmed/false-positive decisions, which refuses to train on fewer than 20 labels rather than guessing.
  • Does it beat sorting by CVSS? An evaluation harness reports precision@k, NDCG and average precision against a CVSS-only baseline, plus ablations for each component, scored on analyst triage as ground truth.

A medium under live attack can outrank a critical nobody is touching. That inversion is the point, and the rationale for every position is shown on the finding.

Automated response

Everything else in AbuseBox answers questions. This acts on the answers.

Dashboard -> Automated Response blocks the addresses attacking you, contains hosts that have started attacking other people, writes the remediation steps for the findings it ranked, re-scans to confirm a fix worked, and notifies when something needs a human now.

Two decisions make that safe enough to ship.

Autonomy is gated on evidence. A SOAR playbook fires on a boolean: one bad detection and a thoroughly corroborated one authorise the same action. Here the belief interval from the fusion engine decides how much autonomy an action gets

  • proportional to confidence, inversely proportional to how much damage it could do. Sending a webhook needs 25% belief; cutting a host off the network needs 85%, almost no unresolved evidence, and tools that agree. The gate reports which criterion failed, so "belief 0.61, needs 0.85" replaces "not confident enough". Evidence of active exploitation raises an item's priority and never lowers the bar to act on it.

The platform holds no firewall credentials. Enforcement is pull-based: it publishes what is in force and your perimeter fetches it on a timer. Giving AbuseBox a firewall token would make this service the most valuable target on your network, since anything that can write arbitrary rules is worth more than the findings it stores. Pulling inverts that, and revoking the whole capability is deleting one cron line.

# nftables - replaces the set atomically, so re-pulling is safe
*/5 * * * * curl -sf -H "X-API-Key: abx_..."     https://abusebox.example.com/response/feed/nftables | nft -f -

Nothing is ever sent to an attacking address. Every artefact is a rule for your own perimeter: no scan-back, no probe, no retaliation. You cannot block your own assets or a public resolver. Everything applied automatically expires, automatic actions are capped per hour, and every decision keeps a snapshot of the evidence that produced it.

The default mode is observe: it records what it would do and applies nothing. Run it that way for a fortnight, read the plan each morning, then decide.
